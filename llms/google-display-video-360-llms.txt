# Google Display & Video 360

> The Display & Video 360 API automates programmatic display, video and audio buying: partners and
> advertisers, campaigns, insertion orders, line items, ad groups and ads, creatives and ad assets,
> audiences, inventory sources, and the assigned targeting options that decide what a line item buys.
> One REST surface at https://displayvideo.googleapis.com, version v4, 179 operations.
> Google OAuth 2.0 only — there is no API key. Enterprise product, no self-serve signup, no published
> API pricing. Generated by API Evangelist on 2026-08-13; Google publishes no llms.txt for this API
> (probed developers.google.com/llms.txt, developers.google.com/display-video/llms.txt,
> displayvideo.googleapis.com/llms.txt, marketingplatform.google.com/llms.txt — all 404).

## How to call it correctly

- Auth: OAuth 2.0 authorization code. Authorize at https://accounts.google.com/o/oauth2/v2/auth, token at https://oauth2.googleapis.com/token. Scopes: `https://www.googleapis.com/auth/display-video` (full), `.../display-video-mediaplanning` (campaign entities + invoices), `.../display-video-user-management`, `.../doubleclickbidmanager` (reports).
- The OAuth token is not sufficient on its own. The Google Account must also have a DV360 user profile with Read only, Standard or Admin permission on the partner or advertiser being addressed, or every call returns 403 PERMISSION_DENIED.
- Pagination: `pageSize` + `pageToken`, response carries `nextPageToken`. Opaque token — pass it back verbatim. 42 operations paginate.
- Updates: every PATCH requires `updateMask`, a comma-separated list of fully qualified field names. Fields in the body but not in the mask are ignored; fields in the mask but not in the body are cleared. This is the most common cause of a write that appears to succeed and changes nothing.
- Filtering and sorting: `filter` (35 operations) and `orderBy` (39 operations).
- Custom verbs: 33 colon-suffixed methods, e.g. `POST /v4/advertisers/{id}/lineItems:bulkUpdate`. Prefer the 12 bulk methods for volume — one bulk call costs one write against quota rather than N.
- Async: SDF generation is a long-running operation. Start it, then poll `sdfdownloadtasks.operations.get`. Failures surface on the finished Operation, not on the call that started it.
- Errors: `{"error": {"code", "message", "status"}}` where `status` is a google.rpc.Code name. Branch on `status`, never on `message`. Not RFC 9457.
- Idempotency: none. No idempotency key exists. A retried create is a second create — dedupe client-side.
- Quotas: 1500 total / 700 write requests per minute per project; 300 total / 150 write per minute per advertiser. Five methods cost 5x write quota. Exhaustion returns 429 RESOURCE_EXHAUSTED with no rate-limit headers of any kind. Increases cannot be requested.
- Events: none. No webhooks, no callbacks, no push. Poll.

## Data model

Partner > Advertiser > Campaign > InsertionOrder > LineItem > AdGroup > AdGroupAd is the spine; creatives, ad assets, channels, sites, location lists, negative keyword lists, invoices and assigned targeting options hang off it. IDs are opaque numeric strings with no type prefix, but every entity also carries a Google resource `name` of the form `advertisers/{advertiserId}/lineItems/{lineItemId}`, which is self-describing.

- [Data model](https://raw.githubusercontent.com/api-evangelist/google-display-video-360/refs/heads/main/data-model/google-display-video-360-data-model.yml): 31 entities, 24 relationships, derived from the spec.

## Not available

- No official MCP server. Every DV360 MCP server on the market is third-party.
- No A2A agent card on any Google host probed.
- No webhooks, events or AsyncAPI.
- No sandbox, test mode or test credentials — you develop against a live DV360 account.
- No first-party CLI.
- No published status page for this API specifically.
- No self-serve signup, free tier, trial or published API pricing.
